# Benchmarking

VVM uses Criterion as its only benchmark framework.

Criterion is the source of truth for:

- measurement;
- warm-up and sampling;
- outlier analysis;
- statistical comparison;
- named baselines;
- throughput reporting; and
- HTML reports.

VVM does not add a parallel benchmark runner, a custom baseline format, a custom
comparison script, or benchmark execution in CI.

## What The Suite Measures

Milestone 12.6 benchmarks cover:

- pure-Rust runtime hot paths such as packed values, randomization, scoreboards,
  testbench overhead, schedulers, and coverage internals;
- build-time metadata and code-generation work in `vvm-build`;
- `cargo-vvm` orchestration and reporting flows; and
- native Verilator-backed DUT execution for representative examples.

These measurements help contributors compare a change against a saved local
baseline on the same machine.

## What The Suite Does Not Claim

The suite does not claim:

- universal performance numbers across machines;
- CI-grade regression gates;
- hard pass/fail thresholds for acceptable slowdowns; or
- equivalence to other simulators, cocotb, UVM, or handwritten C++ benches.

Criterion baselines are machine-specific and environment-specific. Treat them as
local before-and-after evidence, not release guarantees.

## Local Workflow

Capture a baseline before a performance-sensitive change:

```bash
just benchmark-save-baseline NAME=before-feature
```

Implement the change, then compare against the saved baseline:

```bash
just benchmark-compare-baseline NAME=before-feature
```

Run a focused target when you only changed one area:

```bash
just benchmark-target vvm-core schedulers --save-baseline before-scheduler-change

# Implement the scheduler change.

just benchmark-target vvm-core schedulers --baseline before-scheduler-change
```

Run the complete suite without saving or comparing a baseline:

```bash
just benchmark
```

## Baselines And Reports

Criterion stores benchmark data under `target/criterion`.

- Saved named baselines live under the same local tree.
- HTML reports are generated by Criterion there as well.
- Remove an obsolete local baseline by deleting its directory from
  `target/criterion`.

Do not commit the full `target/criterion` tree.

## Interpretation

Use Criterion's own output and reports to decide whether a change is acceptable.

- Prefer comparisons on the same machine, OS, toolchain, and Verilator setup.
- Check both time and throughput for workloads that report units such as cycles,
  transactions, events, or artifacts.
- Review the statistical comparison instead of reacting to a single sample.

VVM intentionally does not enforce hard automatic regression thresholds yet.
Those decisions remain a developer and reviewer judgment call.
